# offset → keyset 分页迁移方案（规划，未实施）

| | |
|---|---|
| 状态 | 🔴 **规划，本轮不动手** |
| 触发条件 | 任一端点真正开始翻页（前端 `loadInbox` 之外的第二页被请求） |
| 影响端点 | `GET /records` · `GET /messages` · `GET /messages/arrivals` · `GET /pet/me/postcards` |
| 前置 | 见 §5，其中 `postcards` 的排序未定义是**硬前置** |

## 1. 为什么现在不做，以及为什么迟早要做

前端实测反馈把两种漂移分开了，这个区分决定了优先级：

| 表现 | 后果 | 前端能否自救 |
|---|---|---|
| **重复**（同一张卡在两页各出现一次） | 无害 | ✅ 能。按 `cardId` 归并天然吸收，已钉用例 |
| **漏**（边界那条被跳过） | 该条不显示、暖点不亮 | ❌ **不能。静默丢失，前端无从发现** |

漂移只在**翻页时**发生。当前 `loadInbox` 只取第一页、根本不请求 `nextCursor`，所以 P0 阶段
一次漂移都不会发生。**这不构成现在就改的理由。**

但反过来也成立：**开翻页那天，keyset 是前置条件而不是优化项。** 因为「漏」这一类
没有任何下游能兜住——服务端少给一条，前端就是不知道少了一条。

🔴 **前端已明确建议把「消息中心分页」做成一个独立事项统一做。** 四个端点共用同一个
`paginate()`，零敲碎打地一个个换，中间态是「有的端点 cursor 是偏移量、有的是复合键」，
比现在更难判断哪个端点该用哪种游标。**要换一起换。**

## 2. 现状的确切形状

共用一个偏移分页器：

```java
// EchoApi.paginate() —— 全量物化 → 内存排序 → subList
private Map<String, Object> paginate(List<Object> all, int cursor, int limit) {
    int from = Math.max(0, cursor);
    int to = Math.min(all.size(), from + lim);
    data.put("nextCursor", to < all.size() ? String.valueOf(to) : null);
}
```

🔴 **注意「全量物化」**：`store.records(accountId)` 一次取回该账号**全部**记录，排序、过滤、
切片都在内存里。所以换 keyset 不只是换游标格式，**真正的收益要等下推到 SQL 之后才拿得到**；
只换游标格式而仍然全量物化，能修正确性，修不了性能。这两件事要分开评估，不要混为一谈。

四个端点各自的排序键：

| 端点 | 排序键 | 方向 | 次级键 | 问题 |
|---|---|---|---|---|
| `/records` | `RecordEntry.createdAt` | DESC | **无** | 同毫秒两条时顺序不稳定 |
| `/messages` | `MessageEntry.createdAt` | DESC | **无** | 同上 |
| `/messages/arrivals` | 该卡回应的 `max(createdAt)` | DESC | **无** | 排序键是**派生且可变**的，见 §4.3 |
| `/pet/me/postcards` | 🔴 **未定义** | 🔴 **两端不一致** | 无 | 见 §4.4 |

## 3. keyset 方案

### 3.1 游标形状

游标从「第几条」变成「上一页最后一条是谁」：

```
cursor = base64url( "<sortTs>:<id>" )
```

判定式（DESC 页，行值比较）：

```sql
WHERE ("createdAt", "id") < (:ts, :id)
ORDER BY "createdAt" DESC, "id" DESC
LIMIT :n
```

`(createdAt, id)` 构成**全序**：`createdAt` 给主顺序，`id`（雪花，全局唯一且单调）拆同毫秒的平局。
有了全序，「上一页最后一条」就唯一确定了下一页的起点，中途插入或删除都不再移动这个起点——
这正是 offset 做不到的地方。

### 3.2 为什么必须是 base64 而不是 `"<ts>:<id>"` 明文

游标要**不可解释**。明文游标一定会被下游当成可计算的东西用（拼一个、加一个、比大小），
一旦有人这么用，游标格式就再也改不动了。编码一层是为了把「这是个不透明令牌」这件事
变成物理事实，不是为了省字节。

### 3.3 契约影响：比预想的小

🟢 **`nextCursor` 在 wire 上已经是 `string`**（今天的值恰好长得像整数，但类型是字符串），
`cursor` 入参也是 query string。**所以 OpenAPI/TS 类型一个字都不用改。**

需要改的只有服务端解析：`ctx.queryInt("cursor", 0)` 换成解游标。

🔴 **顺带修一个当前就存在的缺陷**：`queryInt` 在解析失败时**静默回落到 0**。

```java
try { return Integer.parseInt(v.trim()); }
catch (NumberFormatException e) { return def; }   // ← 0
```

也就是说客户端传一个非法游标，服务端**不报错**，安静地返回第一页。在「加载更多」语义下
这会把第一页再追加一遍，且客户端拿到的 `nextCursor` 又是第二页，可以一直循环下去。
换 keyset 时，非法游标应当返回 `BAD_PARAM`，**不要保留静默回落**。

## 4. 逐端点影响面

### 4.1 `/records`

最直接的一个。`id` 是雪花、`createdAt` 是毫秒，`(createdAt, id)` 直接可用。

🔴 **唯一的坑是 `scope` 过滤**：今天是「全量取回 → 过滤 → 切片」，过滤在切片之前，所以结果是对的。
换成 keyset 后，过滤条件**必须进判定式**。若写成「按 keyset 取 n 条 → 再过滤」，
页内会被过滤掉若干条，返回不足 n 条，而客户端通常把「不足 n 条」理解为「到底了」——
于是**剩下的记录再也翻不到**。这是把「漏一条」升级成「漏一大截」，比现在更糟。

### 4.2 `/messages`

与 `/records` 同形。注意 `POST /messages/read` 会改 `read` 字段但不改 `createdAt`，
所以标记已读**不影响**游标稳定性。

### 4.3 `/messages/arrivals` —— 🔴 排序键是派生且可变的

这个端点的「一行」是一张卡，排序键是该卡全部回应的 `max(createdAt)`，
**不是某个存储列，而且新回应到来时会变大。**

游标形状仍是 `(最新时刻, cardId)`，但要认清它带来的性质变化：

- 时刻只增不减（回应只会新增，不会回退），所以一张卡在 DESC 序里**只会往前（往新）移动**。
- 往前移 = 移进「已经翻过」的区域 → 该卡**再出现一次**。
- 🟢 **也就是说 keyset 把这里的「漏」全部转化成了「重复」**，而重复前端按 `cardId` 归并天然吸收。

**这是 keyset 在本端点上最值钱的性质**，比性能重要得多：它把一类前端救不了的错误
换成了一类前端已经能救的错误。offset 在同样场景下给出的是「漏」——插入一张卡使后续整体
下移一位，恰好跨在页边界上的那张卡被跳过，且没有任何人会发现。

⚠️ 但要注意：`(最新时刻, cardId)` 只在**服务端按卡折叠**的前提下是一行一卡。当前实现已经
这样做了（`EchoApi.reactionArrivals` 按卡推进游标），所以这个前提成立；🔴 **如果哪天改回
按回应行分页，本节的结论全部作废**，那时同一张卡会横跨两页，游标语义也不再是「上一张卡」。

### 4.4 `/pet/me/postcards` —— 🔴 硬前置：现在根本没有确定的顺序

这是四个里唯一一个**换 keyset 之前必须先补设计**的：

| 实现 | 顺序 |
|---|---|
| `PgEchoStore.postcards` | `ORDER BY "createdAt" ASC` —— **升序** |
| `InMemoryEchoStore.postcards` | 直接返回底层 `List`，**插入序，无排序** |

两处不一致本身就是缺陷（同一份数据两种后端给出不同页），而且方向与 `/records`、`/messages`
的 DESC **相反**。keyset 的正确性完全建立在「全序且两端一致」之上，所以顺序是先决条件：

1. 先定明信片该按什么排、升序还是降序（🔴 **这是产品问题不是技术问题**——明信片是时间线叙事，
   最早的一张在最上面可能是有意的），
2. 两个 store 实现对齐，
3. 再谈 keyset。

在第 1 步有结论之前，这个端点不要动。

### 4.5 不在射程内的 `/relations`

`GET /relations` 返回 `Map.of("items", views)`，**没有 `nextCursor`，压根没有分页**。
且它的排序键是「置顶 > 在线 > 最近活跃」这样一个**复合且高频变动**的键（`online` 随时翻转），
keyset 在这种键上不成立。若将来亲友列表要翻页，是另一个课题，不要顺手并进来。

## 5. 前置条件清单

| # | 前置 | 阻塞谁 |
|---|---|---|
| 1 | 明信片的排序口径拍板 + 两个 store 对齐 | `/postcards` |
| 2 | 非法游标改为 `BAD_PARAM`，去掉静默回落到 0 | 全部 |
| 3 | `scope` 等过滤条件下推进判定式 | `/records` |
| 4 | 决定是否同时把全量物化改成下推 SQL（正确性与性能可分两步） | 全部 |
| 5 | 确认 `/messages/arrivals` 仍按卡分页（§4.3 的前提） | `/arrivals` |

## 6. 明确不做的

- **不做双游标兼容期。** 游标是短命的（一次会话内用完即弃），不存在需要兼容的存量游标。
  为它加一层「旧格式也认」的解析分支，是给一个不存在的问题写代码。
- **不改 wire 类型。** 见 §3.3。
- **不顺手给 `/relations` 加分页。** 见 §4.5。
